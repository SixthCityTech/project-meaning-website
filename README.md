# Project Meaning — Phase 1 working prototype

Next.js App Router. `npm install`, `npm run dev`, `npm run build`. This is a draft for local/staging review, with `noindex` metadata; it is not a production release.

The homepage reads the public Project Meaning Utilis feed on the server by default, revalidating after 60 seconds. An empty feed shows no placeholder articles. `/articles/[slug]` reads the same brand-scoped endpoint and sanitizes HTML. The client requires explicit `published` and `public` fields plus Project Meaning brand or site eligibility. Reader tokens are not used because the memo says they can expose previews. On 2026-11-04 the public feed and detail returned one article, `why-project-meaning`; its title, body, author, image and FAQs rendered locally. Cross-brand syndication and authorization semantics remain unverified. The CMS returns a `projectmeaning.org` canonical while the handoff specifies `projectmeaning.com`; canonical and structured data are withheld pending domain reconciliation. The staging site remains noindex. The CMS context endpoint also returned unrelated brand data: do not use it without explicit scoping validation.

Homepage content lives in `content/site.json`; `tina/config.ts` contains a preliminary homepage-only schema and `npm run tina:dev` is the intended local editor command. Tina installation, configuration, real edit/preview/PR workflow, and account/plan remain to be verified. Other pages, navigation, imagery and cards are still in code and need content models before the requested page-editing workflow is complete. The initial contact mechanism is the owner-supplied email link to info@projectmeaning.com. The owner does not want analytics or a mailing list at launch; a reviewed privacy statement describing actual hosting and email practices remains pending.

The owner accepted the current primary logo and homepage imagery for now and the supplied journey logos for the prototype. The page uses crops of the supplied moodboard; higher-resolution individual source images have not been located and were requested as a later ZIP. Asset provenance and publication rights remain to be verified. Verify the `.com` domain and deployment target. No Hestia, DNS, GitHub or production settings were changed by this prototype.

## Article presentation and outstanding delivery checks

`/articles` provides an archive using the CMS card image when available. The article page shows CMS hero, byline, takeaways, topics, body, a site invitation, answer summary and visible FAQs. HTML is sanitized; missing bodies, unsupported markup and unapproved body image URLs produce an unavailable-content notice and server diagnostic rather than silently discarding article content. Images are restricted to the CMS uploads origin. A published/public article must have a nonfuture publication date and explicit Project Meaning brand or site assignment.

The CMS feed currently contains full article data, including substantial nested brand context; a compact/paginated listing and its completeness semantics have not been verified. Related readings, author profile routes, source and correction mappings, cross-brand syndication behavior, social metadata, canonical/JSON-LD, and indexable sitemaps remain unverified or unimplemented. No production publication or indexing approval is implied. Publication, unpublication, site removal and update propagation have not been tested end-to-end; the current fetch revalidation is 60 seconds and can retain a previous response within that interval. Outage behavior and cache invalidation require release testing.
